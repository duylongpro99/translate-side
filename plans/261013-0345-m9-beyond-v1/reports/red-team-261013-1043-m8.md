# Red-team review: M8 Beyond v1 plan (2026-10-13)

Scope: `plans/261013-0345-m8-beyond-v1/plan.md` and phases 01-08, checked against the working tree on master.
Requested scope (`docs/plans/M8-beyond-v1.md`) and the accepted pricing are treated as constraints.

## Finding 1: The lock silently turns off the import guard that keeps a key from following a redirected connection
**Severity:** Critical
**Location:** phase-02 Requirements (lines 44-47, "import with keys ... encrypt when the lock is on"); Related files (`portable.ts:575-605`)
**Flaw:** The plan treats `portable.ts:575-605` only as a place to encrypt imported keys. That same block holds the redirect guard, which removes a stored key when an imported file points an existing connection at a different address. The guard only sees a key when the stored value is a plain string, so an encrypted envelope (an object) counts as "no key". The plan never mentions this.
**Failure scenario:** The lock is on. The user imports a shared settings file in which connection `openai` now points at `https://evil.example/v1`. `hasKey` is false for the envelope, so `keyAction` is `'none'`, no removal happens, and the redirect report says no key is affected. On the next unlock, `resolveConnection` decrypts the key and the first job sends `Authorization: Bearer sk-...` to the attacker's host. The lock is meant to protect keys, but here it makes them easier to steal.
**Evidence:** `src/shared/portable.ts:599-602` (`const hasKey = typeof saved === 'string' && saved !== ''`; only then is the key added to `removeSecrets`); `:581-584` (`current === key`, `typeof current === 'string'`). Same string-only checks elsewhere: `src/entrypoints/options/Providers.tsx:70`, `src/shared/providers.ts:326, 547, 671` (through `readApiKey`, `src/shared/settings.ts:194`). DESIGN §8 states the rule this guard enforces (comment at `portable.ts:588-589`).
**Suggested fix:** Phase 2 must list every `typeof … === 'string'` check on `secret:*` values in `portable.ts` (`:581-584`, `:599-602`) and route them through `keyState(...) !== 'none'`. Add a test: lock on, import a file that redirects a keyed connection, and assert the envelope lands in `removeSecrets` and the report says `removed`.

## Finding 2: Nothing retries a job after unlock; the listener the plan names never sees a session write
**Severity:** High
**Location:** phase-02 Architecture (line 62, "storage.onChanged → translator retries stopped jobs (the existing secret-change retry, translator.ts:579)"); Requirements line 39 ("the job retries after unlock without a second click")
**Flaw:** Unlock writes the derived key to `storage.session`. The retry the plan relies on listens only to `storage.local` changes whose key starts with `secret:`. The panel's session listener only handles selection keys. So the done criterion "translation prompts for unlock instead of failing" only partly holds: the job never resumes. Options also stays stale, because its reload listeners filter on local `secret:` keys.
**Failure scenario:** The panel shows the unlock prompt, the user unlocks, the session key is written, and no listener fires. The job sits in its `keysLocked` stop until the user presses Retry. The planned e2e ("unlock → the job completes") fails, or gets weakened to click Retry. Options still shows "Locked" next to every key until it reloads.
**Evidence:** `src/entrypoints/sidepanel/translator.ts:578-580` (`onLocal`: `k.startsWith(SECRET_PREFIX)` only), `:570-576` (`onSession`: `tabIdFromSnippetKey` only, `continue` otherwise), `:611, :616` (where they are registered); `src/entrypoints/options/Providers.tsx:117`, `src/entrypoints/options/Options.tsx:72` (local `secret:` filter).
**Suggested fix:** Name the session key constant (for example `keylockSession`), and in phase 2 add an explicit `onSession` branch that calls `retryStopped()` when it appears. Do the same in the two Options listeners. Make the e2e assert completion with no second click.

## Finding 3: The engine retry wrapper ends the stream at the first `tool_call`
**Severity:** High
**Location:** phase-07 Requirements (lines 54-55, "a `tool_call` counts as output for retry and fallback (`sawText` is set)"); Step 5
**Flaw:** The plan assumes the retry wrapper only needs `sawText` set. In fact the wrapper treats every event that is not `usage`, an early `error`, or `text` as terminal: it flushes usage, yields the event and returns. A `tool_call` reaches that branch.
**Failure scenario:** The model makes two parallel tool calls (the plan's own test case, step 4). The wrapper yields usage early, then the first `tool_call`, then stops. The second call and `done{stopReason:'tool_use'}` are dropped. Phase 8's loop sends one tool result for an assistant turn that declared two `tool_calls`. OpenAI-compatible endpoints reject that round with a 400 ("tool_call_ids did not have response messages"), and Anthropic rejects a missing `tool_result`. Every Deep-mode chunk with parallel calls then falls back to `refine` or fails. The adapter-level unit tests in step 4 do not catch this, because they bypass `withRetry`.
**Evidence:** `src/engine/retry.ts:122-126` (`// Terminal: done, or an error after text.` `if (usage !== undefined) yield usage; yield event; return;`); `:118-121` (only `text` continues). `src/engine/fallback.ts:81-83` (sets `sawText` only on text).
**Suggested fix:** In phase 7, change `retry.ts` so `tool_call` sets `sawText`, is yielded, and continues. Only `done` and `error` are terminal. Add a wrapper-level test: two tool calls, then `done(tool_use)`, through `withRetry` and the fallback chain, asserting both calls and the stop reason come out in order.

## Finding 4: The byte-identity check cannot fail on the risk it is said to mitigate
**Severity:** High
**Location:** phase-04 Requirements (lines 39-40, 50-52); Risks line 145 ("A lexer misreads a string as a comment … the identity check fails closed"); Success criteria lines 122-124
**Flaw:** `codeOutsideComments` compares bytes outside the spans the same lexer produced. If the lexer reads code as a comment, that code sits inside a "comment" span in both the original and the spliced text, so the check passes by construction. It only catches splice bugs, not lexer errors. The family table also builds in misreads: CSS has no `//` comments but sits in the `//` family. JSX text with URLs sits in the C family too.
**Failure scenario:** A Docusaurus page shows `background: url(//cdn.example.com/a.png);` or `<p>See https://x.dev/docs</p>` in a `jsx` block. The lexer takes `//cdn.example.com/a.png);` as a line comment, the model "translates" it, and the identity check passes. The panel shows altered code with no warning. The guarantee "Code stays byte-identical" breaks, and no test notices.
**Evidence:** The phase-04 C-family list includes `css scss less` (line 39); `fixtures/docs/docusaurus-code-blocks.json` has `css`, `jsx` and `tsx` code segments (checked: codeLang set `md|jsx|js|bash|css|diff|tsx|ts|py|java`). The criterion "all code fixtures" is partly met by default: `fixtures/docs/mkdocs-material-admonitions.json` has 17 code segments with no `codeLang` at all, and `fixtures/docs/mdn-promise-then.json` uses `javascript`, which is not in the list, so nothing is extracted from them.
**Suggested fix:** Add an independent check, either a test corpus of strings, URLs, regexes and CSS `url()` that must yield zero spans, or a re-lex of the spliced text that must produce the same non-comment token stream. Drop `//` for CSS (`/* */` only) and leave out `jsx/tsx` text children, or bail on them. Add `javascript`, `typescript` and `shell` aliases. State in the done criterion how many comments each fixture actually yields, so an empty extraction cannot pass it.

## Finding 5: Phase 5's provider list removes M7's translation-memory provider for Pro users, and the gate cannot sit where the plan puts it
**Severity:** High
**Location:** phase-05 Requirements (line 45, order `[brief, glossary, site-style, domain, context-tail]`; lines 46-47, "byte-identical to v1"; lines 56-57, gate in `defaultEngine`); plan.md Cross-Plan table (`domain-packs` row)
**Flaw:** M7 phase 6 adds `translation-memory` to `DEFAULT_CONTEXT_PROVIDERS` after the tail. Phase 5 replaces the list with an explicit one when entitled, and that list leaves memory out. Even if memory is added back last, site style (100) and domain (300) now come before the tail, so memory's share of the 1,500 budget shrinks. M7 says memory gets "what is left, up to 400". The "byte-identical to v1" test is the wrong baseline once M7 has landed. Separately, `defaultEngine` and `engineFor` are synchronous and return a `TranslationEngine`, while `featureAvailable` returns a Promise. So "the one gate call site" in `defaultEngine` cannot exist without making engine construction async, which the plan does not list.
**Failure scenario:** A paying user turns on a domain pack, and their own corrections stop reaching the prompt. M7's Balanced/Best gain from translation memory quietly disappears for exactly the users who paid. No test notices, because phase 5 compares against v1 prompts.
**Evidence:** `src/engine/context/budget.ts:33` (`DEFAULT_CONTEXT_PROVIDERS = [documentBriefProvider, glossaryProvider, contextTailProvider]`); `plans/261013-0348-m7-stronger-translation/phase-06-translation-memory-provider.md:39-41` (memory appended after the tail, up to 400 of 1,500); `src/entrypoints/sidepanel/jobs.ts:1240` (`engineFor(...): TranslationEngine`, sync), `:1296`, `:1311` (`defaultEngine` sync).
**Suggested fix:** Build the entitled list as `DEFAULT_CONTEXT_PROVIDERS` with the two new providers inserted, not a hand-written list. Test that memory is still present and record its share. Resolve the entitlement and the snapshot asynchronously before `engineFor` (near `jobs.ts:899`) and pass them in. Change the byte-identity baseline to "the prompts as M7 left them".

## Finding 6: The PDF reader skips the denylist and never-translate list, and its origin grant doubles as a site grant
**Severity:** High
**Location:** phase-06 Design decision items 2-3 (lines 41-46); Security (line 180, "nothing is fetched on navigation"); Related files (DESIGN.md edit limited to the §1 line)
**Flaw:** The built-in denylist and the user's never-translate list are checked only against the tab or page URL. The reader tab's URL is `chrome-extension://…/pdf.html?src=…`, and the `src` it fetches is never checked. The plan says nothing about either. The same `chrome-extension:` URL is also classified `restricted`, so the panel's normal path refuses the reader tab. Whatever special case the implementer adds will skip the denylist unless the plan requires it. The reader then fetches with `credentials: 'include'`. The origin granted at the click is a lasting `https://host/*` permission, which the extension already treats as "this site may be re-injected with no gesture". Reloading the reader tab or restoring the session fetches again with cookies, which contradicts "nothing is fetched on navigation".
**Failure scenario:** The user has put `bank.example` on never-translate. They open `https://bank.example/statements/2026-09.pdf` and press Open in reader. The grant is requested, the statement is fetched with the session cookie, and its text goes to the LLM provider. That breaks DESIGN §8 ("A built-in denylist is never read or sent", plus the user list). The `bank.example/*` grant persists, and the extension now holds a permission DESIGN §8 says it requests only for provider endpoints and allowlisted sites.
**Evidence:** `src/shared/denylist.ts:7, 39` (only `http: https: file:`; `chrome-extension:` → `restricted`); `src/shared/inject.ts:38` and `src/extract/index.ts:79` (the only `classifyUrl` gates, on the page URL); `src/shared/sites.ts:101-112` (`hasSitePermission`: an origin grant means re-injection with no gesture); `DESIGN.md:805, 819-821`.
**Suggested fix:** Require `classifyUrl(src)` and the never list on `src` in the reader boot and in the panel button, with e2e cases for a denylisted host and a never-listed host. Prefer `credentials: 'omit'` by default. If cookies are needed, make it a visible choice with a privacy line. Offer `permissions.remove` after the fetch, or list PDF grants separately so allowlist logic does not treat them as sites. Update DESIGN §8's permission sentence, not only §1.

## Finding 7: The Firefox request firewall would pass every extension request silently
**Severity:** High
**Location:** phase-03 Step 7 (line 104, "Keep the request firewall (`fixtures.ts:152-157`) on both targets"); Security (line 159)
**Flaw:** The firewall decides that a request came from the extension only if it came from a service worker or from a frame whose URL starts with `chrome-extension://`. Firefox MV3 runs an event page, not a service worker, and its pages are `moz-extension://`. So `from` is always `undefined`: the request is answered 200 with an empty body and never reported. The fixture also blocks on `context.waitForEvent('serviceworker')`. Whether Playwright's Firefox can route requests from `moz-extension` contexts at all is unverified, and Spike B does not test it.
**Failure scenario:** A Firefox-only regression sends a request to a third-party host, for example the define-term origin or a font CDN, from the panel. The Firefox e2e job stays green. The one automated check behind "nothing leaves for a host the user did not choose" is missing on the new target, and the plan's Security section claims it is there.
**Evidence:** `e2e/fixtures.ts:151-156` (`request.serviceWorker() ? 'worker' : request.frame().url().startsWith('chrome-extension://') ? 'panel' : undefined`; report only when `from !== undefined`); `:159-160` (`waitForEvent('serviceworker')`); `:150` comment (the rule this check enforces).
**Suggested fix:** Add to Spike B a negative test: the extension page fetches `https://off-list.example/`, and the harness must report it on Firefox. Generalise the classifier to any `*-extension://` frame. If Playwright cannot intercept extension-origin requests on Firefox, the phase records BLOCKED for this guarantee instead of claiming it.

## Finding 8: The bundle-budget steps cannot be done as written, and `.mjs` files are named wrongly
**Severity:** Medium
**Location:** phase-01 Step 10 (lines 83-84, "only to add the new `chunks/gemini.js` line; confirm … no other entry changed beyond rounding"); phase-06 Step 7 (lines 124-125); plan.md Key risks (lines 136-139)
**Flaw:** `--update` rewrites every entry and the total to the current measured size plus 10%, not just the new line. The current budget was set "before the diagnostics log", so every entry changed since then will move, and the "only the new chunk changed" check fails or gets waved through. For PDF, the plan only widens the file filter to `.mjs`. The name-normalising regex strips content hashes only from `.js`/`.css`, so every hashed `pdf.worker-<hash>.mjs` becomes a new unlisted name on each build, and the check fails the next time a hash changes.
**Failure scenario:** The phase 1 implementer runs `--update`, sees a dozen entries move, and either stops (blocked) or accepts a budget that also loosened unrelated lines. In phase 6, CI's `check:bundle` goes red on the next pdf.js bump, or on any change that alters the worker's hash.
**Evidence:** `scripts/check-bundle.mjs:30` (budget rebuilt from all `names`), `:21` (`/-[\w-]{8}(\.(js|css))$/`), `:16` (filter); `scripts/bundle-budget.json` note ("before the diagnostics log … (2026-10-12)").
**Suggested fix:** Add an `--add <name>` mode that sets only new entries and the total, or have the step tell the implementer to hand-edit the one line and the total. Extend the regex in `:21` to `(\.(m?js|css))$` in the same commit as the filter.

## Finding 9: `define_term` validation checks the term's shape, not where it came from, and the hostile-page test only covers the easy case
**Severity:** Medium
**Location:** phase-08 Requirements (lines 53-61); Step 3 (lines 121-122); Security (lines 189-192); Requirements line 52 against line 68
**Flaw:** "Never receives raw page text" is enforced only as a format: 1-48 characters, at most 3 words. Every accepted term still comes from page text the model chose under page influence. The only adversarial test is "the whole paragraph", which is rejected anyway. A hostile or confidential page can drive 20 well-formed lookups that copy names, case numbers or codenames to the dictionary operator. The Security claim "cannot exfiltrate to the attacker" holds only if the endpoint's logs are not attacker-readable, and the plan never states that as a condition on the endpoint choice. Also, line 68 ("No tool writes anything") contradicts `flag_ambiguity` (line 52), which appends model-written, page-steered text to `segment.final.notes`. The plan does not say what happens to those notes when M7's acceptance rule rejects the candidate.
**Failure scenario:** A legal brief marked confidential is read in Deep mode with "Look up terms online" on. An injected line, or simply the model's own choice, sends "Project Halcyon", "Acme Holdings" and a docket number to Wiktionary. This is up to 20×48 characters of the document per job, each a valid term. ROADMAP item 14's intent (no page text off device except to the provider) is met in letter only.
**Evidence:** `ROADMAP.md:452` (the constraint and the exfiltration threat it names); `DESIGN.md:814-816` ("The model has no tools" claim being rescoped); `src/engine/types.ts:162-163` (`notes?: string[]` on `segment.final`, the field `flag_ambiguity` writes).
**Suggested fix:** Only allow terms that are dictionary words: require the term to appear in a source segment and not to be mostly capitalised proper nouns or digits, or require it to be a single lowercase word. Lower the per-job cap. Add a test where a hostile segment asks for 20 valid-looking proper nouns, and assert how many get through. Restate line 68 to include `flag_ambiguity`'s write, and define what happens to notes when a candidate is rejected.

## Finding 10: The eval pass bars use a gate margin built for a different sample size and settings
**Severity:** Medium
**Location:** phase-08 Success criteria (lines 150-153, "+0.20 on 4–6 passages"); phase-05 Success criteria (lines 118-120, "+0.20 terminology on 6–9 passages"); phase-01 Success criteria (lines 102-105, "within 0.20 of 4.24")
**Flaw:** The 0.20 margin is `max(2 × SD of 5 repeated run means, 0.2)` over 23 passages. Each M8 bar applies it to one run over 4-9 passages scored 1-5 in whole points. On 5 passages, one judge score moving one point shifts the mean by exactly 0.20, so pass or fail comes down to a single noisy judgment. Phase 1's comparator (4.24) was run at chunk 1500 × 2, while phase 1 tests at `--chunk-tokens 400`. The matrix itself warns its rows are not like-for-like. Terminology is already at 4.48 against a ceiling of 5, so a +0.20 terminology gain on the existing scale leaves little room above the noise.
**Failure scenario:** Agentic "beats" refine because the judge gave one passage a 5 instead of a 4, and Deep mode ships as the Pro lead on noise. Or a real gain is rejected, also on noise. Gemini-native fails or passes on a chunk-size change rather than on the adapter.
**Evidence:** `eval/gate.json` (`"marginRule": "max(2 × sample SD of the 5 run means, 0.2)"`, terminology baseline 4.478, built from 5 baseline runs); `docs/provider-matrix.md:15, 21` (23 passages; the Gemini row at chunk 1500 × 2; "The rows are not like-for-like").
**Suggested fix:** For phases 5 and 8, require repeated runs (at least 3 per arm) and a margin of 2×SD measured on that subset, or a passage-level win rate (for example agentic ≥ refine on at least 80% of passages), plus the deterministic hit-rate metric. For phase 1, either run the native adapter at chunk 1500 × 2 to match the row, or re-run the OpenAI-endpoint row at 400 alongside it.
