# Provider matrix (M4-F)

Quality, cost and speed of each provider on the same 23-passage eval set (149 translatable segments, English → Vietnamese, `single-pass` / `translate@1`, natural style), run with the Node harness (`pnpm run eval -- --set eval --provider …`) and scored by the pinned judge (`ds/deepseek-v4-pro`, judge@1). ROADMAP §7 lists "provider matrix" under M5 docs and the M4 row asks for "a provider matrix of quality and cost"; this page is where it lives (docs/provider-matrix.md), and M5's docs page can link or copy it.

Run on 2026-10-09. Harness runs are kept in `eval/runs/m4f-*` (summary, judge scores, outputs); the full comparison table is `docs/provider-matrix/eval-report.md`; extension runs and screenshots are in `docs/provider-matrix/`.

## Scope: what changed from plan §3 #1 (decision G5)

Plan §3 #1 names five providers: Anthropic direct, OpenRouter (both protocols), Gemini, Ollama (Qwen 7–8B) and LM Studio. By the user's decision G5 (2026-10-09) local Ollama and LM Studio are replaced by **Ollama cloud**, because no local model is available. Anthropic direct was skipped by the user (no key): **not run — skipped by user (no key)**. `OPENROUTER_API_KEY` arrived later in the day, but the account holds 0 credits (`/credits`: total 0), so every paid model answers 402 "quota" and only `:free` models (50 requests a day) can run: the OpenRouter rows below are blocked on credits, not on a key. APIBOX (`AIBOX_API_KEY`), the app's default provider, is an extra row.

Ollama cloud hosts no Qwen model. Its list on 2026-10-09: `kimi-k2.7-code`, `minimax-m3`, `kimi-k3`, `mistral-large-4`, `nemotron-3-super`, `nemotron-3-ultra`, `glm-5.3-flash`, `kimi-k2.6`, `nemotron-3-nano:30b`, `gpt-oss:20b`, `glm-5.3`, `gemma4:31b`, `gpt-oss:120b`, `mistral-large-3:675b`, `deepseek-v4-pro:0813`, `deepseek-v4.1-flash`, `minimax-m2.7`, `glm-5.2`. Run: **`gemma4:31b`** (a multilingual model, the closest to "Qwen-class, small") and **`gpt-oss:20b`** (the smallest model offered; the only data on small-model behaviour).

## The matrix

**The rows are not like-for-like in settings.** Each row used its provider's own settings (the "settings" part of its first cell: chunk tokens × requests in flight, quirks). The Gemini and APIBOX runs used the harness defaults, chunk 1500 × 2 in flight; the Ollama rows used the `ollama-cloud` preset's 1200 × 4. Per-call latency is a fair comparison across rows; **whole-set and page wall times are not** (different chunk sizes and concurrency, a pause in the Gemini run, a provider's load on the day). The settings are in each run's `summary.json`.

Judge scores are 1–5 means over 23 passages (fidelity / naturalness / tone / terminology, "overall" is their mean). No human scores exist for these runs, so the judge-versus-human check is not available here; the judge is the same one used for every earlier baseline, so the rows are comparable with each other and with `eval/runs/baseline-*`.

### Extension side (§3 #1: "harness and extension")

`scripts/eval/ext-run.mjs` loads the built extension (`.output/chrome-mv3`) in Chrome for Testing 1243 with Playwright, serves `fixtures/sites/goblog-pipelines.html` from 127.0.0.1, seeds one provider (connection, profile, routing, key; the privacy notice acknowledged), opens the panel, and waits for the job to end. Each run ends in a screenshot of the panel; the job bar's text, cost and count of failed blocks are in the `.json` beside it.

Method limits, stated plainly: a headless run cannot press the toolbar icon or answer Chrome's permission prompt, so the driver (a) adds `host_permissions` for 127.0.0.1 and the provider's origin to a temporary copy of the manifest, and (b) does what the worker's action handler does (inject `content-scripts/content.js`, write the tab's `access:<id>` record) instead of clicking. The panel, the job engine, the provider client and the storage reads are the real built code. The permission prompt itself and the real Alt+T gesture remain covered by unit tests and by a human check.

## What each provider showed

- **Gemini via its OpenAI endpoint.** Works with no quirks. Fastest median call (3.5 s). Judge 4.24, the lowest of the three working models, mostly naturalness (3.78) and humor (3.88). One segment needed the re-request (a `script` check) and was repaired. By far the most expensive of the three that report a cost (≈ 21× APIBOX on the same set).
- **APIBOX `qwen3.8-flash`.** Highest judge score (4.49), cheapest (nominal $0.0015 per set; the gateway's USD prices are unverified), a 7.5 s median call, slower than Gemini's, because the app's thinking policy (chunk 1 off, later chunks `minimal`) is applied. The extension run took 73.6 s for the page against Gemini's 21.6 s (one run each, so the gap may be the thinking policy, the gateway or the day's load; it was not measured further).
- **Ollama cloud `gemma4:31b`.** No quirks needed, 0 lost, 0 repaired, judge 4.46 (best naturalness, 4.39; best docs, 4.66). Per-call time on this run was 13.5 s median (25 s max) but is load-dependent (a rerun measured 3.9 s, note ³); the preset's `maxConcurrency: 4` makes the page itself as fast as Gemini (23.3 s). No cost figure: the plan is a subscription, so the panel shows no cost (the Usage and cost section would count tokens only).
- **Ollama cloud `gpt-oss:20b` — the small-model finding (plan §8 risk).** With the preset's default quirks (`{}`, no reasoning policy) the model is unusable: it thinks before it answers, the thinking is not reported in `usage` (reasoning tokens 0) and counts against the output cap the engine sets (≈ 660 tokens for a chunk), so every one of the 46 calls ended with `stop: max_tokens`; many answers were empty or cut mid-segment, 127 of 149 segments were lost in the harness and 63 of 73 blocks failed in the panel. With a profile quirk `reasoning: { control: 'effort', lowest: 'low', reserveTokens: 6000 }` (the same mechanism as APIBOX's Qwen policy, S2) the run recovers to 0–1 lost (harness) and 72 of 73 (panel; one block failed and is retryable). Even then quality is well below the others (judge 3.48; humor 2.67; the model translates literally and misses idiom), so a 20 B reasoning model is a poor default for translation. No model in the 7–8 B class could be tested, so the plan's "consider single-pass for < 7B" question (below) stays open.

## Decisions and open items

1. **G5 applied.** Ollama cloud stands in for local Ollama and LM Studio; the two local presets are unchanged and untested against a real server in this phase.
2. **Local chunking (plan §5, "decided from harness data").** *Open.* There is no local model to measure, so the local presets keep `maxConcurrency: 1` and their smaller `chunkTokens`, and `single-pass` stays the strategy at every size. The only small-model data is `gpt-oss:20b` above; it says a small reasoning model needs a reasoning policy before chunk size matters. Decide when a 7–8 B local model can be run (Ollama or LM Studio on a machine that has one).
3. **One product fix (item 5); nothing else changed.** The other genuine provider failure (`gpt-oss:20b` with default quirks) is a missing per-model reasoning policy on an unlisted model, not a wrong preset: `ollama-cloud` has no default model, and the working model (`gemma4:31b`) needs none. **No product change in M4 (ruling for this milestone).** *Open decision for a later milestone:* give the `ollama-cloud` preset a `defaultModel` of `gemma4:31b`, or add a learned quirk for a `max_tokens` stop with an empty or cut answer (reasoning policy learned like the other quirks), or both. Until then a user who picks a reasoning model sees blocks that failed with Retry failed.
4. **Harness change.** `scripts/eval/run.ts` gained `ollama-cloud` (default model `gemma4:31b`), `openrouter` and `openrouter-anthropic` (default model `anthropic/claude-haiku-4.5`) provider entries. New: `scripts/eval/ext-run.mjs`, `scripts/eval/detect.ts` (`pnpm run eval:detect`).
5. **OpenRouter Auto-detect: a bug found and fixed (decision).** `pnpm run eval:detect` (the Settings' Test connection with protocol `auto`, run against live OpenRouter) first reported the OpenAI path as "The model list is not OpenAI-shaped": OpenRouter's `/api/v1/models` answers `{data, total_count, links}` with no `object: "list"`, which §4.2.5 step 2 required, so Auto-detect found only the Anthropic path. `src/llm/openai.ts` now also accepts a non-empty listing with no `object` field whose entries are not Anthropic's (`type: "model"`); a test covers it for both adapters. After the fix the run (`docs/provider-matrix/detect-openrouter.json`, no key in it) reports `detected: ["anthropic-messages","openai-chat"]`, saves `openai-chat` (the model is not `claude-*`), and keeps per-protocol auth (`x-api-key` on `/api`, bearer on `/api/v1`), with a 1-token chat call passing on both (free nemotron model). Note the OpenRouter *preset* is fixed to `openai-chat`; only the "Custom — either" preset uses Auto-detect.
6. **OpenRouter free-model run.** Both harness entries (`openrouter`, `openrouter-anthropic`) reach the gateway and the Anthropic-protocol path accepts `Bearer` and returns `<seg>` answers, but the only free models are reasoning models whose output cap fills before the answer (the gpt-oss pattern above), so the run says nothing about quality.
7. **Rows waiting on credits.** After credits are added to the OpenRouter account: `pnpm run eval -- --set eval --provider openrouter --price 1,0.1,5 --concurrency 1` (OpenAI protocol) and `--provider openrouter-anthropic` (Anthropic protocol), both on `anthropic/claude-haiku-4.5`; run them one after the other (parallel requests were refused for exceeding in-flight credit). Anthropic direct: `--provider anthropic` if a key is ever added. Then `pnpm run eval:judge -- <run>` and `pnpm run eval:report`. Update this table; the quality and cost half of the OpenRouter rows is unproven until then (the Auto-detect half is shown in item 5).
8. **Judge calibration.** None of these runs has a human sheet, so the "judge vs human" check is absent; differences under about 0.25 between the top rows (APIBOX 4.49, gemma 4.46) are inside the judge's own noise and should not be read as a ranking.
9. **Small models and the glossary (plan §8) — untested.** Plan §8 also says small models "ignore the glossary". The eval set has no glossary and none of these runs passed one, so this page says nothing about it; `gpt-oss:20b` is the only small model measured, and only on translation quality.
